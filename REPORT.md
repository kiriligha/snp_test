# Отчёт

## Правило

Для каждой недели t считаю, сколько продукта можно отгрузить суммарно к концу t (запас, поступления, что успеет собраться из компонента); заявке недели w даю не больше минимального остатка этой величины по неделям от w до конца горизонта. Приоритеты обслуживаются строго по очереди; внутри приоритета заявки идут по неделе, затем по request_id: сначала каждой min_lot, потом добор до qty. Сборка только под отгрузки и как можно позже.

## Журнал решений

**Строгий приоритет** понимаю сильнее условия: старшие получают максимум возможного, и только потом младшие получают что-либо. Отверг «старшей достаточно ненулевой отгрузки»: младшая забрала бы запас, недоданный старшей.

**Порядок внутри приоритета** — по хронологии: ближний спрос надёжнее, дальний может закрыть ещё не запланированное поступление. Отверг пропорциональное деление: в CASE_04 оно дало бы 45 и 135 вместо 60 и 120, ни одна заявка не покрыта целиком.

**Полнота при дефиците** — всем хотя бы min_lot, затем по хронологии; отверг «целиком первому». Пример CASE_05: запас 100, один приоритет, R-1 (неделя 2, 40, min_lot 10), R-2 (неделя 3, 100, min_lot 70). Порядок по неделям: R-1 40, остаток 60 < 70, R-2 0, покрыто 40 из 140. Выбранное правило: R-1 10, R-2 70, R-1 добирает 20, покрыто 100 из 140. Будь ещё заявка приоритета 2, простой порядок отдал бы ей эти 60 в обход строгого приоритета.

**Впрок не собираю**: остаток компонента остаётся компонентом, лишний продукт появляется только из-за кратности (CASE_07: собрано 100, отгружено 99). Отверг сборку всего компонента сразу: гибкий компонент превращается в продукт без спроса.

**Ничьи** (один приоритет, одна неделя) разрешаю по request_id. Отверг порядок строк во входе: он зависит от выгрузки.

**Некорректные данные** проверяю до расчёта, вывожу все ошибки сразу, весь запуск завершается кодом 2. Отверг тихое исправление (округлить 12.5, выбросить строку с X): это план на данных, которых никто не присылал. Отверг пропуск битых кейсов: противоречит коду 2, хотя для ночного пересчёта правильнее.

## Проблемы во входных данных и постановке

- CASE_03: продукт X в поступлениях, дробный спрос 12.5, R-3 в двух неделях, приоритет 0 при шкале от 1. Это ошибки, вход даёт код 2. Повторённая строка поступления: идентификатора нет, суммирую как две поставки.
- Файлы кейсов в CRLF, остальные в LF: читаю оба. В CASE_06 строки не по порядку недель: заявки сортируются.
- Не сказано, сгорает ли непокрытый спрос: принял, что сгорает. Считается ли частично покрытая заявка покрытой: считаю непокрытой. Что делать с одним битым кейсом среди многих: останавливаю весь расчёт.

## Три вопроса аналитику

1. Старшей заявке нужен максимум объёма или достаточно min_lot? Во втором случае младшие затем конкурируют наравне, и меняется ядро распределения.
2. Непокрытый спрос сгорает или его можно отгрузить позже своей недели? Перенос отменяет привязку заявки к неделе, на которой построено правило.
3. R-3 в неделях 4 и 5 — одна заявка с графиком поставки или ошибка выгрузки? От ответа зависит ключ заявки и применение qty и min_lot.

## Границы применимости

Проход по min_lot идёт по хронологии, а не по оптимуму: при запасе 100, A (неделя 1, 60, min_lot 60) и B (неделя 2, 100, min_lot 100) правило отгрузит 60, хотя можно 100. Заявка без min_lot может быть урезана ради min_lot более поздней заявки того же приоритета. Строгий приоритет может пожертвовать большим объёмом младших ради малого прироста старших. Сборка в последний момент не оставляет запаса на задержку поставки. Сведение к одному ресурсу верно только для одного компонента и одного продукта без мощностей и сроков годности.

## Масштаб

Расчёт кейса линеен по числу заявок × недель: 10 000 заявок на 52 недели — сотые доли секунды; 5 млн кейсов по ~10 заявок — минуты на одном ядре, в окно укладывается. Узкое место — чтение и память: файлы читаются целиком. Нужны потоковое чтение входа, отсортированного по кейсу, параллельный расчёт по партициям кейсов (процессы, машины) и запись в файлы или базу. Битый кейс не должен останавливать пересчёт: его откладываем с отчётом. Связанные узлы сети считать по уровням, внутри уровня параллельно.

## Большая сеть

Первым сломается сведение к одному ресурсу: при общем компоненте выбор «в какой продукт собрать» становится частью распределения, нужен учёт по каждому компоненту, в пределе оптимизационная модель. Несколько уровней потребуют обхода по уровням и передачи приоритета исходной заявки вниз по цепочке. С мощностью линий сборка в последний момент станет невыполнимой, придётся собирать заранее в недели со свободной мощностью. Срок годности не позволяет суммировать запас по времени, учёт придётся вести по партиям.

## Частичный пересчёт

Кейсы независимы, пересчитывается только затронутый. Новая заявка приоритета p не меняет результат для приоритетов выше: пересчёт можно начать с сохранённого состояния перед p. Сдвиг поступления меняет доступность во всех следующих неделях, кейс проще пересчитать целиком (миллисекунды). Ручная корректировка партии ломает предпосылку, что сборка выводится из отгрузок: партию фиксирую как вход и пересчитываю остальное. Пересчёт может отнять объём, обещанный младшему клиенту: нужен замороженный горизонт.

## Использование ИИ-ассистента

Claude Code (агентный режим): разбор постановки и данных, код. Ядро, тесты, корректировку и решения о правиле и составе итоговой версии делал я.

- **Обсуждали:** трактовку строгого приоритета (выбрал лексикографическую, см. журнал). Правило с отдельным проходом по min_lot ассистент предложил после разбора CASE_05.
- **Сгенерировано:** часть чтения (snp/load.py), вывод и коды завершения (snp/cli.py), скрипт демо-входа (tools/make_demo.py).
- **Переписано:** первая версия была избыточной (отдельный модуль проверки плана, генератор нагрузки, система предупреждений), урезал до необходимого.
- **Проверка:** ожидаемый план каждого кейса посчитан вручную и зафиксирован в тестах. В ядро по одной вносил ошибки: убрать проход по min_lot, сортировать по неделе вместо приоритета, округлять сборку вниз, игнорировать срок сборки, не учитывать будущие недели, убрать request_id из сортировки; каждую ловит хотя бы один тест. Отдельно план проверялся на 5000 случайных кейсах независимым кодом (не в репозитории): границы min_lot и qty, кратность сборки, невозможность добавить объём недопокрытой заявке даже за счёт всех младших.
